# 人工验收作业单（需要人按 / 听 / 看 / 动手的项）

用途：`SPLIT-PLAN.md` §5.0 的 **H 组**统一登记在这里。机器项（编译、扫描、烧录校验、
串口回文）不写在本表，见 `evidence/INDEX.md` 与各 `split-s*.log`。

固件：`build-split-s9/pm_f103_demo.hex`（S9b 提交，`git log -1` 可查），已 `-v` 回读校验通过。
（M1–M8 原登记时对应 `build-split-s8`；S9a/S9b 未改按键、继电器、电机、蜂鸣器、ADC、蓝牙代码。）
条件：板子通电、ST-Link 已断开（或至少不占用）、串口 **COM11 @ 115200 8N1**，
串口工具的 DTR/RTS 保持无效（避免打开端口即复位）。

状态取值：`PENDING`（未做，默认值）/ `PASS`（有证据）/ `FAIL`（有证据，需回退）。
**写 PASS 必须同时填"证据"列**（日志文件名 + 行号或字节数），否则仍算 PENDING。
判"未验证"的项不得写成通过。

## 0. 通用准备与记录

1. 打开 COM11，保存原始日志到 `evidence/manual-<项>.log`（UTF-8，带毫秒时间戳）。
2. 按键/字节类测试先发 `OLED off` 关掉 live 刷屏，减少串口噪声；做完发 `OLED live` 恢复。
3. 每条命令以 `\r\n` 结尾，命令大小写不敏感。
4. 判读陷阱（来自 `docs/PROTOCOL.md` §5）：BLE 回包会被拆成多个气泡，按**总字节数**判，
   不数气泡个数；`DIST` 现在恒回 `DIST err=disabled`（TIM2 已划给电机）；`PWM sweep`
   会阻塞约 5.4 s，期间 `hb`/OLED 停摆属预期。

### M1-e 边界分析（源码口径，2026-11-20）

1. 扫描方式与周期：`keypad_dev_service(now)` 在主循环里**每轮调一次**
   （`src/app/main.c:132`），循环本身无固定延时，正常情况下周期只有数毫秒。
   但同一循环后面的 `oled_ui_service()`（`src/app/main.c:144`）要整页写 I2C，
   实测整页传输 `ms=98`（`OLED live ok ms=98`，`oled_ui_job.c:187` 注明该值是
   真实 8 页传输时间），且 live 模式每 500 ms 触发一次 → **每 500 ms 里约有 98 ms
   主循环被占住，这期间按键一次都采不到**。
2. 消抖门槛：`keypad_dev.c:11` `#define KEY_DEBOUNCE_MS 20u`；判定在
   `keypad_dev.c:81-86`——电平变化时先记 `raw_since`，之后每轮若 `pressed == raw`
   且 `now - raw_since >= 20 ms` 才接受为稳定电平。**不是"连续 N 次采样"计数**，
   而是"保持时间"判据，所以 20 ms 是下限、实际还要加上下一次采样到来的等待。
3. 判在哪个边沿：计数与 `last` 只在**按下边沿**更新（`keypad_dev.c:87-90`）；
   文本在两侧边沿都输出（`keypad_dev.c:94-95`）；LED 跟随消抖后电平（`keypad_dev.c:91-93`）。

**理论最短可捕获按压时长**：

- 最佳情况（循环没被 OLED 占住）：`20 ms + 一个循环周期（数 ms）` ≈ **25–30 ms**；
- 最坏情况（整段按压落进 98 ms 的整页传输窗口）：raw 一次都采不到 → **完全不可见**；
  要"保证可捕获"，按压必须长于 `20 + 98 ≈` **118 ms**。

对上第二轮数据：20 组实测按压时长 31–172 ms，其中 12 组 **< 100 ms**
（31/47/48/61/63/63/64/65/66/67/74/79/80/83/85/95/98），正好落在"可能整段被
I2C 窗口吞掉"的区间。因此 650 ms 空白里漏掉一记短按**在设计边界之内**，
不能据此判定固件缺陷。

复现口径：以约 0.5 s 的节拍（远大于 118 ms 边界）连点 20 次，若人报数与固件数一致，
即证明轮询/消抖逻辑无系统性漏计。

## M4 电机（PA0/PA1，DRV8833，TIM2 20 kHz）

1. `MOTOR stat` → 期望 `dir=stop duty=0% hz=20000 arr=3599 ccr1=0 ccr2=0`。

3. `MOTOR duty 80` → 转速明显加快，方向不变。
4. `MOTOR rev 50` → 轴**反向**转。

出处：`docs/PROTOCOL.md` §4.9（"fwd 对应哪个机械方向未验证"，本次补齐）。

**回包取证（2026-11-20 10:22:59–10:23:14，`evidence/manual-m4-motor.log`）**：

```
[   334ms] MOTOR stat dir=stop duty=0%  hz=20000 arr=3599 ccr1=0    ccr2=0
[   609ms] MOTOR fwd  ok dir=fwd  duty=50% hz=20000 arr=3599 ccr1=1800 ccr2=0
[  3936ms] MOTOR stop ok dir=stop duty=0%  hz=20000 arr=3599 ccr1=0    ccr2=0
[  6943ms] MOTOR rev  ok dir=rev  duty=50% hz=20000 arr=3599 ccr1=0    ccr2=1800
[  9927ms] MOTOR stop ok dir=stop duty=0%  hz=20000 arr=3599 ccr1=0    ccr2=0
[ 12926ms] MOTOR stat dir=stop duty=0%  hz=20000 arr=3599 ccr1=0    ccr2=0
```

四段动作时刻：0.609 s（fwd）/ 3.936 s（stop）/ 6.943 s（rev）/ 9.927 s（stop）。
`ccr1=1800` 与 `ccr2=1800` 均为 `arr=3599` 的 50% 取整（3599×0.5≈1800），
fwd 只给 CH1、rev 只给 CH2，stop 双 0；**没有"报 ok 但 CCR 为 0"的矛盾**。
**轴的实际转向、转速与停转现象尚未目视**，M4 仍为 PENDING。

**只读诊断（2026-11-20 10:27–10:30，`evidence/manual-m4-dbg.log`）**：用户报轴完全不转，
为此加了临时只读子命令 `MOTOR dbg`（直接读寄存器，不经模型层缓存）：

```
MOTOR dbg cr1=0x00000081 ccer=0x00000011 ccmr1=0x00006868 arr=3599 psc=0 cnt=505+1049 crl=0x22008BBB
MOTOR dbg ... cnt=1269+1751 ...      <- fwd 之后
MOTOR dbg ... cnt=3027+3029 ...      <- rev 之后
MOTOR dbg ... cnt=365+845 ...        <- stop 之后
PWM dbg ... mapr=0x00000000          <- AFIO->MAPR：TIM2 无重映射
```

逐位判读：
- `cr1=0x81` = CEN(bit0)=1 + ARPE(bit7)=1 → 计数器在跑；
- `ccer=0x11` = CC1E(bit0)=1 + CC2E(bit4)=1 → 两通道输出使能未被清；
- `ccmr1=0x6868` = OC1M/OC2M=110（PWM 模式 1）+ OC1PE/OC2PE=1；
- `cnt` 两次采样均有非零跳变（+544/+482/+2/+480），stop 后仍在走（TIM2 不随方向停）；
- `crl=0x22008BBB`：PA0、PA1 低两个半字节均为 `B`（复用推挽 50 MHz），初始化后未被改写；
- `mapr=0x00000000`：TIM2_REMAP=00，CH1/CH2 就在 PA0/PA1。

结论：固件侧寄存器状态全部正确，定时器在计数、通道使能、引脚复用与重映射均无误，
`ccr1/ccr2` 与占空比换算一致；**MCU 侧没有可再查的软件异常**，问题在 PA0/PA1 之外。
